# Nexa Chat — Render ↔ Altare encrypted gateway

**Purpose:** a persistent custom HTTPS address `https://nexachat.devs.li` for an already-running Nexa Chat on Altare. All accounts, database, media, SMTP and payments stay on Altare. The gateway on Render stores no chats, files or passwords.

## 0. Requirements

- Your registered `nexachat.devs.li` subdomain on DEVS.LI (already created).
- A GitHub account to deploy the small gateway to Render.
- An existing Altare Nexa Chat 4.4 with `.env` and working `app.py`.
- A free Render account (Web Service, Python). Free Render can sleep and has usage limits. Do not use this configuration for high-stakes production or real payments until availability/security have been reviewed.
- Phone with Termux and SFTP access to Altare.

## 1. Make the Render gateway

1. Create a GitHub repo named `nexa-chat-gateway` (public is OK, **NO secrets in repo**).
2. Upload `gateway.py`, `requirements.txt` and optionally `render.yaml` from `render_gateway/` into **repo root**. Files must be top-level, not nested inside a ZIP.
3. Render Dashboard -> New -> Web Service -> connect GitHub repo. Select Free instance and Python environment.
4. Set:
   - Build command: `pip install -r requirements.txt`
   - Start command: `uvicorn gateway:app --host 0.0.0.0 --port $PORT --proxy-headers`
   - Environment variable `NEXA_PUBLIC_HOST=nexachat.devs.li`
   - Environment variable `NEXA_BRIDGE_SECRET=<secret generated by Termux setup below>`
5. Start the service. You'll receive a real URL like `https://your-service-name.onrender.com`. The actual name will differ.

## 2. Generate bridge secret and upload the agent to Altare

1. In Termux unzip `NexaChat_Altare_Bridge_v1.zip` into a folder, then run `bash deploy_bridge_termux.sh`.
2. Enter the real Render URL from step 1.
3. The script prints a random secret. Copy that exact value to Render Environment -> `NEXA_BRIDGE_SECRET`, save/redeploy. **Do not paste this secret into ChatGPT or public posts**.
4. Enter `YES` to upload bridge files through SFTP. Altare should be stopped before changing files.
5. Change Altare Startup to `PY_FILE=nexa_bridge.py`, `REQUIREMENTS_FILE=requirements.txt`, then start.
6. Look for `[Nexa Bridge] Secure gateway connected` in Altare Console.
7. Open `https://YOUR-SERVICE.onrender.com/__nexa_health`. Response should include `"altare_connected": true`.

The script keeps `app.py`, `.env`, `data/chat.sqlite3`, `data/media/*` and `nexa_https.py`. It merges Python requirements; does not replace the application or database.

## 3. Link DEVS.LI to Render

1. Render -> your Web Service -> Settings -> Custom Domains -> Add Custom Domain: `nexachat.devs.li`.
2. In DEVS.LI Dashboard edit **existing CNAME** for `nexachat.devs.li`.
   Replace `de-fra01.altare.global` with the **exact** `<your-service>.onrender.com` shown by Render. Do not add `https://`, a port, or a path.
3. Save DNS; then return to Render and Verify. Let the Render-managed HTTPS certificate become active.
4. Open **`https://nexachat.devs.li`**. Try login, profile and sending one message.

Don't point a CNAME at `trycloudflare.com`, and don't disable HTTPS-only login. DNS propagation/TLS issuance may take some time.

## 4. What this does and limitations

Traffic path: browser HTTPS -> Render gateway -> **authenticated encrypted WSS** -> Altare agent -> local Nexa Chat app over 127.0.0.1. Browser WebSocket chat messages traverse the same link. Cookies and account tokens stay on an encrypted connection between providers, but Render necessarily processes live requests in memory. The bridge is not end-to-end encrypted messaging.

- An active agent sends regular connection health messages. Under Render's published rules, incoming WebSocket messages count as activity. **This is not an uptime guarantee**. Render Free may cold-start, restart, suspend a high-traffic site or consume its monthly 750 instance-hours quota.
- Render Free Web Services are documented as **testing/hobby**, not production. Free service filesystem is ephemeral; we deliberately store all persistent data on Altare.
- Gateway cap: up to 16 MiB per request, 24 MiB response; video uploads larger than this will fail. Uploading media is less efficient because of the WebSocket relay.
- Keep your Render bridge secret private. Rotate it in both Render and Altare if compromised.
- If the bridge goes offline, visitors get HTTP 503 instead of revealing insecure login endpoints.
- Only one Altare agent and one Render instance are supported by this simple bridge. A larger user base requires an architecture upgrade.
- Other domains are rejected by the proxy if `NEXA_PUBLIC_HOST` is set. Use the `onrender.com/__nexa_health` path for troubleshooting.

## Troubleshooting

- Render /__nexa_health `altare_connected=false`: agent not connected. Check Altare Startup (`nexa_bridge.py`), requirements and gateway token.
- `403` in agent WebSocket: mismatch between `NEXA_BRIDGE_SECRET` in Render and local `data/nexa_bridge.env`.
- Login returns `426`: check that `PY_FILE=nexa_bridge.py` and `PUBLIC_ORIGIN=https://nexachat.devs.li`. Don't turn off HTTPS_ONLY.
- `421 Unknown hostname`: this is expected if you try to open the raw `onrender.com` gateway URL while `NEXA_PUBLIC_HOST=nexachat.devs.li`. Only the health endpoint is public there.
- Domain SSL error: confirm Render Custom Domains is Verified and DNS CNAME points to Render, not Altare.
- Upload `413`: exceeds proxy cap.
- Old `nexa_https.py` remains in place; to revert, set `PY_FILE=nexa_https.py`, start, and use the temporary Cloudflare HTTPS URL (if it still works).

**No change to payment integration.** This bridge does not connect Kaspi/Platega/SBP and does not qualify a free Render service for payment-provider production rules.
